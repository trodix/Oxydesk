# ADR 009 — Encodage GPU : VA-API derrière `FrameEncoder` (M8)

## Décision
- **Adaptateur `VaapiEncoder`** (`crates/encode`, feature Cargo `vaapi`, désactivée par défaut) : H.264 matériel via `cros-libva`. Il n'ajoute aucune dépendance sur d'autres adaptateurs ; il implémente le port `FrameEncoder` existant.
- **`AutoEncoder`** (même crate) : choix du backend à la **première image** (VA-API a besoin de la taille). `--encoder auto|vaapi|openh264` dans `rdsktp`, `rdsktp-agent` et `bench`. `auto` (défaut) bascule sur openh264 si VA-API est indisponible (pas de nœud DRM, pas de pilote, pas d'encodeur H.264) ; `vaapi` et `openh264` ne basculent jamais.
- **Flux produit** : Constrained Baseline/Main/High (selon le pilote), CBR, sans B-frames, 1 image de référence, POC type 2, une tranche, CAVLC, recadrage (surfaces alignées sur 16).
- **En-têtes « packed »** (`h264_headers.rs`) : radeonsi n'écrit pas SPS/PPS ni l'en-tête de tranche (il annonce les en-têtes packed 0x1f). Sans eux, le flux commence par un start code puis des données de tranche invalides. L'application écrit donc SPS+PPS (à chaque IDR) et l'en-tête de tranche (chaque image) : writer de bits, Exp-Golomb, anti-émulation, testés unitairement.
- **`cros-libva` 0.0.13 vendorisé** dans `third_party/cros-libva` (deux correctifs : champs VP9 manquants avec libva 1.23 ; types `EncPackedHeaderParameter`/`EncPackedHeaderData` ajoutés, allowlist bindgen étendue). À re-synchroniser si le crate amont les intègre.
- Conversion BGRA→NV12 sur CPU (BT.601 limité, même matrice qu'openh264) puis envoi vers la surface VA.

## Oracles
- `crates/encode/tests/vaapi.rs` : 30 images 1080p encodées par le GPU, **décodées par libopenh264**, vérifiant types de NAL (SPS/PPS/IDR aux images 0 et 15, P sinon), marqueurs rouge/bleu aux positions attendues, erreur absolue moyenne < 12 (mesuré : 0,98). Ignoré si pas d'encodeur VA-API ou pas de libopenh264.
- Tests unitaires de `h264_headers`.
- Bout en bout local (`rdsktp --test-mode --encoder vaapi` + `rdp-test-client` IronRDP, builds release) : **7/7**, key→pixel p95 34,1 ms (openh264 : 25,4 ms).
- Repli : `LIBVA_DRIVER_NAME=bogus` + `--encoder auto` → openh264 ; `--encoder vaapi` → erreur explicite.

## Mesures (RX 7800 XT, 1080p, release, `bench`)
| Source | VA-API | openh264 |
|---|---|---|
| synthétique (peu de mouvement) | 13,7 ms/image (p95 14,4) | 4,2 ms |
| bruit (pire cas) | 13,2 ms | 32,6 ms |

Le temps GPU est essentiellement constant ; il est dominé par la conversion CPU et l'attente de fin d'encodage. Le GPU ne gagne que sur les contenus lourds ; sur du bureau quasi statique openh264 est plus rapide. L'intérêt du GPU est la **charge CPU** et la tenue en pire cas, pas la latence sur contenu simple.

## Non vérifié / suite
- **Production** : VMware sans GPU → openh264 reste le chemin réel ; le GPU n'y est pas testable.
- NVENC : non implémenté. Chemin `DmaBuf` (import direct de la frame KWin sans copie CPU) : non implémenté, KWin livre du SHM ; ce serait le vrai gain (supprimer la conversion CPU, shader/VPP).
- Session KWin réelle avec encodeur GPU, KRDC/mstsc, build sur Debian 13 (en-têtes libva de trixie vs `cros-libva` vendorisé) : non testés.
- Passthrough GPU dans la VM de test : non fait (optionnel).
- Packaging : la feature `vaapi` n'est pas activée dans les paquets (`libva` en dépendance à décider).
