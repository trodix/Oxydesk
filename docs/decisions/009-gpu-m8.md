# ADR 009 — Encodage GPU : VA-API derrière `FrameEncoder` (M8)

## Décision
- **Adaptateur `VaapiEncoder`** (`crates/encode`, feature Cargo `vaapi`, désactivée par défaut) : H.264 matériel via `cros-libva`. Il n'ajoute aucune dépendance sur d'autres adaptateurs ; il implémente le port `FrameEncoder` existant.
- **`AutoEncoder`** (même crate) : choix du backend à la **première image** (VA-API a besoin de la taille). `--encoder auto|vaapi|openh264` dans `rdsktp`, `rdsktp-agent` et `bench`. `auto` (défaut) bascule sur openh264 si VA-API est indisponible (pas de nœud DRM, pas de pilote, pas d'encodeur H.264) ; `vaapi` et `openh264` ne basculent jamais.
- **Flux produit** : Constrained Baseline/Main/High (selon le pilote), CBR, sans B-frames, 1 image de référence, POC type 2, une tranche, CAVLC, recadrage (surfaces alignées sur 16).
- **En-têtes « packed »** (`h264_headers.rs`) : radeonsi n'écrit pas SPS/PPS ni l'en-tête de tranche (il annonce les en-têtes packed 0x1f). Sans eux, le flux commence par un start code puis des données de tranche invalides. L'application écrit donc SPS+PPS (à chaque IDR) et l'en-tête de tranche (chaque image) : writer de bits, Exp-Golomb, anti-émulation, testés unitairement.
- **`cros-libva` 0.0.13 vendorisé** dans `third_party/cros-libva` (deux correctifs : champs VP9 manquants avec libva 1.23 ; types `EncPackedHeaderParameter`/`EncPackedHeaderData` ajoutés, allowlist bindgen étendue). À re-synchroniser si le crate amont les intègre.
- Conversion BGRA→NV12 sur CPU (BT.601 limité, même matrice qu'openh264) puis envoi vers la surface VA.

## Oracles
- `crates/encode/tests/vaapi.rs` : 30 images 1080p encodées par le GPU, **décodées par libopenh264**, vérifiant types de NAL (SPS/PPS/IDR aux images 0 et 15, P sinon), marqueurs rouge/bleu aux positions attendues, erreur absolue moyenne < 12 (mesuré : 0,98). Ignoré si pas d'encodeur VA-API ou pas de libopenh264.
- Tests unitaires de `h264_headers`.
- Bout en bout local (`rdsktp --test-mode --encoder vaapi` + `rdp-test-client` IronRDP, builds release) : **7/7**, key→pixel p95 34,1 ms (openh264 : 25,4 ms).
- Repli : `LIBVA_DRIVER_NAME=bogus` + `--encoder auto` → openh264 ; `--encoder vaapi` → erreur explicite.

## Mesures (RX 7800 XT, 1080p, release, `bench`)
| Source | VA-API | openh264 |
|---|---|---|
| synthétique (peu de mouvement) | 13,7 ms/image (p95 14,4) | 4,2 ms |
| bruit (pire cas) | 13,2 ms | 32,6 ms |

Le temps GPU est essentiellement constant ; il est dominé par la conversion CPU et l'attente de fin d'encodage. Le GPU ne gagne que sur les contenus lourds ; sur du bureau quasi statique openh264 est plus rapide. L'intérêt du GPU est la **charge CPU** et la tenue en pire cas, pas la latence sur contenu simple.

## Chemin DmaBuf (import GPU, sans conversion CPU)
- **Core** : `FrameData::DmaBuf(DmaBuf { fd: OwnedFd, offset, modifier })` (le fd appartient à la frame).
- **Capture** (`KwinCapture::start_with(.., dmabuf)`) : en plus du format SHM, propose le même format avec le modificateur **linéaire** uniquement (`MANDATORY | DONT_FIXATE`). Si KWin accepte, les frames sont livrées en `DmaBuf` (fd dupliqué) ; sinon le flux reste SHM. Linéaire seulement : le CPU peut toujours relire le tampon en repli.
- **Encodeur VA-API** : import `DRM_PRIME_2` (XRGB8888/XBGR8888) puis conversion BGRx→NV12 par le moteur vidéo (VPP, `VAProfileNone`/`VideoProc`, BT.601 plage réduite, mêmes coefficients que le CPU) dans la surface source de l'encodeur. Contexte VPP créé à la première frame DmaBuf. Si l'import échoue : message unique, puis lecture CPU du tampon (mmap + `DMA_BUF_IOCTL_SYNC`) et chemin habituel. `openh264` lit aussi le DmaBuf par mmap (correct, mais voir mesures).
- **Choix** : `--dmabuf auto|on|off` (`rdsktp`, `rdsktp-agent`, `bench --kwin`). `auto` = vrai seulement si l'encodeur peut utiliser le GPU (`--encoder vaapi`, ou `auto` avec VA-API utilisable). Sans GPU : offre SHM uniquement, comportement inchangé.
- `cros-libva` vendorisé : ajout du type `ProcPipelineParameter` et de `va_vpp.h`.

### Oracles et mesures du chemin DmaBuf
- Test `dmabuf_import_decodes_to_the_source_pixels` : les 30 images sont placées dans un vrai DMA-BUF (memfd + `/dev/udmabuf`, indépendant de VA-API), importées, converties par le GPU, encodées, décodées par libopenh264 ; erreur moyenne 0,98 (identique au chemin CPU) et `gpu_frames() == 30` exigé. Témoin négatif : plage de sortie « pleine » au lieu de « réduite » fait monter l'erreur à 3,97, donc l'oracle détecte une conversion erronée.
- KWin virtuel réel sur la RX 7800 XT (`bench --kwin`, 1080p, release, bureau avec défilement continu) :

| Configuration | Transport reçu | Temps/image (p50) |
|---|---|---|
| VA-API + DmaBuf (import GPU) | 210/210 DmaBuf | **7,3 ms** (p95 7,9) |
| VA-API, SHM + conversion CPU | 210/210 SHM | 14,4 ms |
| openh264, SHM | SHM | 12,2 ms |
| openh264 forcé sur DmaBuf (relecture CPU) | DmaBuf | 268 ms (p95 399) |

- Contrôle visuel : le flux H.264 produit à partir des frames KWin en DmaBuf (`bench --kwin --out`) est décodé par ffmpeg ; l'image (fenêtre Konsole, texte, couleurs) est correcte.
- La dernière ligne justifie `--dmabuf auto` : relire un tampon GPU depuis le CPU est ~20× plus lent que le SHM, donc ne jamais proposer le DmaBuf sans encodeur GPU.

## Risques connus du DmaBuf
- Le tampon peut être réécrit par KWin dès qu'il est remis en file ; la frame est consommée plus tard depuis la boîte aux lettres. Le noyau applique la synchronisation implicite (fences) pour la lecture GPU, mais un déchirement léger reste possible si l'encodeur prend du retard de plusieurs images.
- Les lignes de remplissage (1080 → 1088) ne sont pas répliquées par le VPP (le CPU les réplique) ; elles sont rognées par le recadrage SPS.
- Modificateurs non linéaires (meilleurs pour KWin) non proposés.

## Non vérifié / suite
- **Production** : VMware sans GPU → SHM + openh264 reste le chemin réel ; ni VA-API ni DmaBuf n'y sont testables. Reste à confirmer que KWin y fonctionne tout court (ADR 004 : OpenGL + nœud DRM exigés).
- NVENC : non implémenté (aucun GPU NVIDIA disponible, rien à exécuter).
- Pas rejoué : `vm-test` (VM virgl, build sans `vaapi`) après la modification de la capture ; session RDP complète avec encodeur GPU sur KWin réel (le presse-papiers `wlr-data-control` n'est pas accordé à une session KWin lancée sur le poste de dev) ; KRDC/mstsc ; build sur Debian 13 (en-têtes libva de trixie vs `cros-libva` vendorisé).
- Passthrough GPU dans la VM de test : non fait (optionnel).
- Packaging : la feature `vaapi` n'est pas activée dans les paquets (`libva` en dépendance à décider).
